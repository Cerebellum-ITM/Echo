# Scripting

> Owns headless and composed execution: script mode (`echo <cmd>`), recipes (`echo run`), `sequence`, build mode (`--build`), `report`, `shell-run` and piped `shell`, and the command-log history with `logview`. Last verified: 2026-09-30.

Code: `internal/repl/script.go`, `recipe.go`, `sequence.go`, `build.go`, `report.go`, `silence.go`, `cmdlog.go`, `logview.go`, `shellrun.go`; `internal/cmd/build*.go`, `shellrun.go`, `logview_remote.go`; `internal/config/cmd_logs.go`, `run_report.go`, `last_sequence.go`; `main.go`. Exit codes, root resolution, `-C`/aliases and the non-TTY fail-closed rule are owned by [architecture-and-traps](architecture-and-traps.md); this file only states how scripting uses them.

## Script mode

- `echo <cmd> [args]` runs ONE command through the same frame as the REPL and exits with its code. `RunOnce` builds a headless session via `newSession` (no prompt loop) and calls `dispatchParsed` once, so output is byte-identical to the REPL; `session.exitCode` is only read in script mode. Source: Unit 31, `internal/repl/script.go`.
- `IsScriptCommand` = `dispatchNames` minus `clear`/`exit`/`quit`. `connect` (direct mode) and `run` are handled in `main.go` before it is consulted.
- **The interactivity guard keys on the TTY, not on a mode flag.** Pickers, confirms and `init`/`reset` forms call `requireTTY` (seam `stdinIsTTY`) and return `ErrNonInteractive` -> exit 2 with a hint ("pass the argument", `--force`). Why: one check covers every TTY-less invocation (cron, CI, a recipe, a pipe) instead of threading a `batch` boolean through every `Opts` struct. Rejected: a separate "script" binary or mode.
- A failed `FindRoot` in one-shot exits 2 ("not inside a project") and never falls into the REPL. Which commands are exempt (`projectlessOneShot`, `main.go:236`) is owned by architecture-and-traps.
- **Trap: stdin doubles as input.** `echo run -` and `shell-run -` consume stdin, so any picker or confirm inside such a run fails closed (stdin is not a TTY).

## Recipes (`echo run`)

- `run` is a one-shot-only orchestrator: not in `Registry`/`dispatchNames`, never available inside the REPL. `main.go` routes it before `IsScriptCommand`. Its help sits in a "Scripting" footer outside `helpSections()` so the Registry<->help cross-check stays green (`repl.go`, `scriptingHelpEntries`).
- **Trap: `run` itself needs a compose project.** It is not in `projectlessOneShot`, so outside a project it exits 2 even when every step is remote. `--pick`/`--last` search the resolved project ROOT (`FindRoot` result), not necessarily the shell's cwd (`main.go` passes `root` to `RunRecipe`). Search is top-level only, no recursion.
- Format: one Echo command per line; `#` starts a comment at line start or after whitespace (a `#` inside a token is kept); conventional extension `*.echo`. Recipes are not Echo-managed config: they live wherever the user keeps them (only `--pick`/`--last` discover them). Source: `parseRecipeLines`, `stripComment`.
- **Trap: steps are split with `strings.Fields`** (`runRecipeSteps`): there is no quoting, so an argument containing a space cannot be passed.
- Each step goes through `dispatchParsed` on the SAME session; `dispatchParsed` resets `exitCode`, error/warning counts and `lastOutput`, and `runStepCaptured` resets `lastOutput` again after capturing (meta commands such as `help` do not reset it, so without that a meta step re-captured the previous step's lines). So `startLog`/`finalize`, rendering and the TTY guard apply per step; a step that would prompt aborts the run (exit 2). `sess.recipe = true` makes `help` print flat instead of opening the pager.
- Exit code: all pass -> 0; fail-fast (default) -> the FAILING step's code (unknown command -> 2); `--continue-on-error` runs everything and returns 1 if any failed. Fail-fast is the default because teardown-style best-effort recipes are the exception.
- A single `echo.system.status` INFO line (cli, odoo, env, project, db) is emitted once at the start of a run, not per step. `--last` also prints `latest recipe -> <name>`.
- `--pick` (picker over `*.echo`; none -> `no .echo recipes found in <dir>`, exit 2; Esc -> 3; non-TTY -> 2) and `--last` (newest `*.echo`, no TTY needed, CI-friendly) are mutually exclusive with each other, a path and `-`. Order is creation time newest first: real birthtime on darwin (`Stat_t.Birthtimespec`), `ModTime` elsewhere (Go has no portable birthtime), ties alphabetical, unreadable entries last; the sort is a pure function so tests inject times. `cmd.PickOne` is the exported single-select wrapper that lets `repl` reuse the picker and its TTY guard. Source: Units 39, 52.

### Run recap (Unit 37)

- The recap is Odoo-style `echo.run` log lines, never an ASCII table, so `--log` captures it for free. Per step: empty message with fields `step=i/n status=<ok|failed|cancelled|skipped> cmd=... [silent=...] [warnings=] [errors= exit=] [took=]`. Level: ok INFO, failed ERROR, cancelled/skipped WARNING. Under fail-fast the unreached steps are recorded `skipped`.
- Final `run summary` ALWAYS carries `errors` and `warnings` (even zero) plus `steps ok [failed] [skipped] took`; level ERROR when anything failed.
- Per-command counts reach the runner through the session (`lastErrors`/`lastWarnings`), the same way as `exitCode`; the clock lives in the `runStep` closure so `runRecipeSteps` stays pure and unit-testable. Exit codes are not affected by the recap.

### `--silent` (Unit 41)

- `<step> --silent` drops everything, `--silent=<lvl>` drops that level and below while more severe lines still show. It is stripped by the runner (`stripSilent`) and never reaches the command, so it works for any non-interactive step. An invalid level warns and runs the step un-silenced. Interactive commands (`shell`, `bash`, `psql`) write straight to the TTY and ignore it.
- Mechanism: package var `suppressLevel` (-1 inactive; ranks plain 0, DEBUG 1 ... CRITICAL 5, `silentAll` 99), gated in `sess.print`, `printStyled` and `emitOdooLog`. The level of a printed line comes from its `Kind` (`levelFromKind`), not from the text token. `sess.print`, `printStyled` and `emitOdooLogTo` capture BEFORE the check, so `report --step=N` and the command logs still see silenced lines: suppression is about live noise, not data loss. The runner's own `step N/M`, recap and summary are emitted with suppression off. Safety property: `--silent=warn` never hides ERROR/CRITICAL.
- The package-level switches (`suppressLevel`, `runLogSink`) are valid only because a run is sequential; do not run steps concurrently.

### `--log` (Unit 34)

- Opt-in. No `--log` writes nothing. Default `~/.config/echo/run-logs/<ts>-<recipe>.log`, never the project repo (`config.RunLogsDir`); `--log=<path>` explicit; `--log=<dir>` (e.g. `.`) -> `<dir>/<recipe>.log` (`resolveLogDest`); stdin recipe -> `...-stdin.log`. The space form `--log <path>` is unsupported on purpose: it would collide with the recipe positional.
- Capture is a tee into package var `runLogSink`, set only while `RunRecipe --log` runs. Plain text without ANSI: `sess.print` tees `Line.Text`, `emitOdooLog` tees `plainOdooLogFields` (message plus `key=val`). A log-file creation error only warns; the run and its exit code are unchanged. Independent of `report`.

## `report` (Unit 40)

- Works across processes because every `echo run` and every `sequence` persists a structured record to ONE global file, `~/.config/echo/run-logs/last-run.json` (atomic write; recipe label plus per-step cmd/status/lines with levels). It is not keyed per project, and a plain one-shot command writes nothing: it describes the last recipe or sequence only. A `--run=<id>` selector was left as a possible extension.
- Per-line level: parsed from the text (`lineLevel`: `odooLogPrefix`, Echo's own 4-char prefix `echoLogPrefix` mapped to the full name (`WARN` -> `WARNING`, `ERRO` -> `ERROR`…), `loguruLogPrefix`, `parseLooseSeverity`; keeps ERROR vs CRITICAL distinct); with no token it falls back to the line's `Kind` (`levelFromKind`: faint DEBUG, info INFO, warn WARNING, err ERROR) so inherited traceback frames and unprefixed leveled lines still get a level. `Kind` cannot express CRITICAL, so an explicit token always wins. A line with no level is excluded by any level filter.
- Filters: `--step=N` (1-based), `--level` (exact) vs `--min-level` (threshold, DEBUG < INFO < WARNING < ERROR < CRITICAL), mutually exclusive; `warn` = `warning`. `--copy` uses the OSC52-aware `internal/clipboard`. After the lines, `report` scans the WHOLE run (ignoring step/level filters, since migrations are INFO lines a `--min-level` filter would hide) and emits one `echo.report.migration` line per migrated module.
- Capture is one funnel, `sess.capture` (`cmdlog.go`): `sess.print`, `printStyled` and every `emitOdooLog`/`emitOdooLogTo` line (stdout or stderr), the last through the package var `captureLine` that `newSession` sets, with `Kind` from the level and the plain `plainOdooLogFields` text. So Echo's own `echo.*` lines are in `report`, `copy-last`, the failure auto-copy, records and live files (unit 09 of the console run feed). They are captured, not counted: `runStats`, `lastErrors`/`lastWarnings` and exit codes ignore them. `PrintConfigError` runs before any session and is not captured. Source: `repl.go` `print`/`printStyled`, `logemit.go` `emitOdooLogTo`. The `lastOutput` buffer is capped at 5000 lines (`lastOutputCap`); overflow drops the oldest and sets `truncated`.
- `report` and `logview` are projectless and read local stores only. `logview` is a meta command; `report` is not (it resets `lastOutput`, so `copy-last` after it copies the report) but both are on the command-log skip list (below).

## `sequence`

- Composes argv only; it never opens SSH itself. Flow: tri-state picker (off -> run -> build; badge = order = execution order) -> optional return-only builder (`BuildOpts.SkipDecide`) -> review (Run / Save `.echo` / Copy / Cancel) -> execution through `sess.runStepCaptured`, shared with `echo run`, so step capture, `--silent` and recap behave identically. Own run loop (not `runRecipeSteps`) to control wording and the terminal follow step; loggers `echo.sequence`, `echo.sequence.step`, summary `sequence complete`. Source: Unit 73.
- Remote: `--from <target>` / `--remote` / `-E` apply to the WHOLE sequence with ONE target, baked into every step (`bakeRemote`). `bakeRemote` is command-aware: `--from=<name>` can go to any step, but bare `--remote` only to commands that declare it (`commandAcceptsFlag`); `deploy` and `i18n-pull` do not take `--remote`, so with no `--from` they get no flag and fall back to the directory's `[connect]` binding. A step that already names a target is left alone. v1 does NOT offer a target picker for a flag-less remote sequence (it needs explicit `--remote`/`--from`).
- A trailing follow-`logs` step is forced LAST and the `sequence complete` summary is emitted BEFORE entering the follow, so the Ctrl+C that ends it is not read as a failure. Several follow steps -> warning, only the last follows (`isFollowLogs`, `reorderLogsLast`).
- **Must-build commands** (`mustBuildInSequence`: `deploy`, `i18n-pull`) are interactive at run time, so their selection is captured at build time even if unmarked: deploy gets non-interactive `--commits=<shas>`/`--modules=<addons>` (via `runDeployBuild`), i18n-pull reuses the sequence target via `BuildOpts.From`. The result shows in the review and is replayed by `--last`; a failed must-build aborts. Other builders that fail operationally (e.g. no local stack to list services) degrade to run-as-is with a WARNING; only cancel/quit/non-interactive/abort propagate. A builder cancel cancels the whole sequence (exit 3, nothing ran yet); "nothing to build" runs the command as-is.
- **Observed trap: the i18n-pull builder ignores `SkipDecide`** (`internal/cmd/build_i18npull.go` always calls `decideAction`), so inside a sequence it still shows Run/Copy/Cancel, and the sequence discards the returned action (`sequence.go` uses only `res.Args`): choosing Cancel there does not cancel. `deploy` and `update` builders honor `SkipDecide`. Observed by reading, not run.
- `--last` replays the last EXECUTED sequence: only the Run action persists (`~/.config/echo/last-sequences/<ProjectKey>.toml`, steps with the remote flag already baked, one record per project); Save/Copy/Cancel do not. It needs no TTY (like `echo run --last`), though steps still obey the TTY guard. `--continue-on-error` is supported. Chosen over `-r`, which would clash conceptually with `--remote`.
- Allowlists (`sequenceCommands`, `remoteSequenceCommands`, `sequence.go:28-40`) are guarded by tests: every entry must be in the Registry, every remote entry must be cross-checked against `commandFlags`. `watch` is excluded (a non-terminating step would hang), interactive PTY shells are excluded, `sequence` is not offered inside itself.
- "Save as recipe" writes `<name>.echo` into the project directory: an explicit user action, not an ambient write.
- User-decided via form and mockup (do not re-ask): single Tab tri-state per item; order = selection order, no reorder screen; `logs` forced last; one target per sequence.

## Build mode (`--build`, `-b`)

- Intercepted in `dispatchParsed` before the command switch, only for names in `dispatchNames` (an unknown command with `--build` falls through to the unknown-command path). It must be the ONLY argument (otherwise exit 2). Engine in `cmd` (pickers and data providers are unexported there), session wrapper in `repl` (owns `commandFlags`): `repl` passes the alias-filtered flag list (`buildFlags`: `logs` drops `-c`, every command drops `-E`) into `cmd.RunBuild`.
- Flow: positional picker(s) -> flag multi-select (Tab toggles) -> a value prompt per value-taking flag -> show the composed line -> Run / Copy / Cancel. Run dispatches the composed argv with the normal start/finalize frame; Copy puts the recipe-style line WITHOUT the `echo ` prefix on the clipboard.
- **The composed argv is dispatched tokenized, so each value flag's separator must match what that command's real parser accepts** (`buildFlagValues`: `=` for `--level`, `--out`, `--step`, `--min-level`, `--tags`, `--as`; two tokens for `logs -t`). Changing a parser means changing the table.
- `RunBuild` checks the TTY FIRST, before "nothing to build", so `bash --build` without a TTY exits 2 via `ErrNonInteractive`; inside a recipe build mode always fails closed (exit 2). An empty or cancelled value input drops that flag with `flag --x skipped (no value)` rather than aborting. The builder does not encode mutual exclusions (`update <mods> --all` runs `--all`, ignoring modules; accepted in v1).
- `--build`/`-b` are `universalFlags` (highlight and Tab completion) kept outside `commandFlags`, so per-command help and the cross-check tests stay intact.
- Bespoke builders, because the generic positional-first flow cannot govern their candidate list: `i18n-pull` (target resolved first, then that remote's own modules; bakes `--from=<name>` and `--lang=<lang>`, not a trailing locale positional, because with many module positionals a trailing token is ambiguous to re-parse; `--all`/`--installed` not offered; round-trips through `parseI18nPullArgs`, guarded by `build_i18npull_test.go`), `deploy` (commit and dirty-module picker captured into `--commits`/`--modules`; resolves the target read-only to mute already-deployed commits; never persists manual marks), `update` (resolves WHERE, local/named/linked, and the module SOURCE, project addons vs installed, before the picker; `--installed` is never baked because explicit module names make it a no-op; extras limited to `--i18n`, `--level`). `connect` has no builder (flags only: login needs the remote mint and is interactive at run time). Source: Units 51, 77, 88.

## `shell-run` and piped `shell`

- `shell-run [<file.py>|-]` pipes a Python file to `odoo shell -d <db> --no-http` on stdin (`exec -T`, no TTY), locally or in the remote container over SSH (`--from`/`--remote`/`-E`, `runSSHStream`). Output goes through `emitStreamLine`. Source: Units 59, 62, 63.
- Source `.py` resolution: explicit config `scripts_dir` (relative to the project or absolute) -> a top-level `scripts/` if present -> the project root; always top-level, non-recursive (addons contain thousands of `.py`); picker order reuses the recipe sort. A bare name is looked up in that dir, a path with a separator resolves against the project dir. New command rather than overloading `shell`: keeps the PTY `shell` intact.
- Confirms on prod: local `maybeConfirmProd`, remote `confirmRemoteProd` (reads the TARGET's stage); headless prod needs `--force`.
- Auto-copy: only the script's own stdout (`scriptOutputLines` drops every line with a log level: the shell's boot noise and Echo's own `echo.*` lines, recognized by `lineLevel`) goes to the clipboard on success; the full transcript stays available through `copy-last`; `--no-copy` opts out. `-` with a TTY stdin fails fast ("stdin is a terminal").
- `shell` with a non-TTY stdin is pipe mode: the piped content goes through the same machinery (local or remote), streams Odoo-colored, and does NOT auto-copy (the pipeline consumer owns the output; `copy-last` still works).
- Both handlers read the script body themselves (`os.ReadFile` or `io.ReadAll(os.Stdin)`) and pass it to `cmd.RunShellScript` as `Stdin`, so the record's `script_*` fields are of exactly what ran; a read error goes through `readonlyFinalize` (Command logs, above).

### Odoo shell connection

- `odoo.Shell(conn)` (shared by `shell`, `shell-run`) and every builder in `internal/odoo/cmd.go` pass explicit `--db_host/--db_port/--db_user/--db_password` because `compose exec` bypasses the image entrypoint. `Conn.flags()` skips empty values: an unset `POSTGRES_PORT` once produced a literal `--db_port=` that crashed Odoo with `ValueError: int('')`; callers default the port to 5432. Source: Unit 10.

## Command logs (Unit 81)

- One JSON record per dispatched command (REPL, one-shot, each recipe/sequence step) at `~/.config/echo/cmd-logs/<ProjectKey(abs root)>/<unix-millis>-<command>.json`. Newest-first order falls out of the millis filename prefix, so there is no index file. Lines are level-tagged by the same `captureReportLines` as `report` (text token first, then `levelFromKind`), so `report` and `logview` share the `config.ReportLine` format. Fields include `exit`, `errors`, `warnings`, `truncated`, `from`, `deployed_tip`; `db` and `stage` are always the LOCAL profile's.
- The hook is a `defer` at the TOP of `dispatchParsed` (covers the build-mode early return, fires before `runStepCaptured` resets the buffer, so each recipe step gets its own record). Not recorded: meta commands (`help`, `clear`, `copy-last`), `report`, `logview` (they would recurse or describe the REPL), empty captures, and `disabled = true`. `shell`/`bash` PTY passthrough never reaches the buffer, so only their frames are recorded. `run` itself is not a record (it sits outside `dispatchParsed`; its steps are).
- Saving is best-effort and atomic (`writeAtomic`); a failure never breaks or delays the command. `from` = the named `--from` target or the literal `remote` for bare `--remote` (`remoteRunLabel`), empty for local.
- **Remote fields** (unit 09, `omitempty`): a run that resolves a remote target records `target` (connect target name, or `env:<project>/<env>` for `-E`), `host` (SSH host), `remote_db`, `remote_stage` (the gated stage, `dev`/`staging`/`prod`). They cross the boundary as `cmd.OnRemoteResolved`, called once on the success path of `resolveRemoteShell` and `resolveReverbShell` (`internal/cmd/shell_remote.go`, `reverb.go`); `sess.noteRemoteResolved` keeps the FIRST resolution of a dispatch (`compare --targets a,b` records `a`). They are also in `CmdLogMeta` (`ListCmdLogs`, so `logview --json`).
- **Script fields** (unit 09, records only, not in `CmdLogMeta`): `shell-run` and piped `shell` record `script_path` (empty for stdin), `script_sha256` of the full body, `script_body` cut to 64 KiB at a UTF-8 boundary with `script_body_truncated`, and `script_output_lines` (`scriptOutputLines` texts after the run). Source: `newScriptFields`, `internal/repl/shellrun.go`.
- Nesting: `dispatchParsed` sets the caller's `sess.extras` (`recordExtras`: remote + script) aside, clears it, and restores it after `saveCmdLog`, so a sequence step's target or script lands in the step's record only.
- `link --list --json` skips `finalize` on success (`internal/repl/link.go`): stdout is only the JSON, nothing is captured and no record is written.
- **Live file** (unit 08, commit `e7fd32d`, `internal/config/cmd_logs.go` `CmdLogLive`, `internal/repl/cmdlog.go`): every recordable dispatch keeps `<started-ms>-<command>.running.ndjson` beside its future `.json`, same stem (`saveCmdLog` takes the dispatch's `started`). Line 1 is a header (`schema` 1, `cmd`, `command`, `db`, `stage`, `from`, `started`, `pid`, `truncated` when compacted), then one `{"level","text"}` line per captured line, appended by `sess.capture`. The writer holds `flock` `LOCK_EX` until removal; the file is created as `.tmp`, locked, then renamed, so a prune in another process never sees the final name unlocked. Past 2 MiB it is rewritten in place with the newest buffered lines that fit in 1 MiB under a header with `"truncated":true` (a reader that sees it shrink starts over). When the run ends the record is written FIRST, then the live file is removed. Nested dispatches (sequence steps, build mode) push their own file on `sess.liveRuns`; lines go to the innermost. A failed open means no live file for that run; a failed append removes it and leaves a nil slot so the stack still pops in order. Every live-file failure is silent.
- Orphans: a live file whose lock can be taken belongs to a dead process; `PruneCmdLogs` and `ClearCmdLogs` (`logview --clear`) remove those and never touch a locked one. `ListCmdLogs` reads `*.json` only, so live files never show as runs.
- Retention lives in `global.toml` `[cmd_logs]`: `retention_days = 7`, `max_runs = 500` per project, `disabled = false`; `0` disables that pass (keep forever / unlimited). The table is a pointer (`cmdLogsFile`) so an ABSENT section (defaults) differs from an explicit `0`; `SaveGlobal` writes the section only when non-default. Pruning runs at session start (`Start`, `RunOnce`, `RunRecipe`) and after each save.

## `logview`

- Two-level alt-screen browser (bubbletea) over the history: run list (type to filter on the command line) and log view with a live text filter plus a level filter by THRESHOLD (`tab`/`shift+tab`: all, DEBUG+, INFO+, WARNING+, ERROR+, CRITICAL). Both AND-compose. Threshold rather than exact level because it composes better with the text filter ("only INFO" in practice means "hide DEBUG").
- **Filtering is block-aware, unlike `report`** (`filterLogLines`): a block is a timestamped header line plus its continuation lines (a traceback). The level gate looks at the header, the text gate passes if ANY line of the block matches, and a leading headerless block shows only on "all". The block boundary is the timestamped prefix (`entryHeaderLevel`), deliberately not the stored `ReportLine.Level`, because traceback frames inherit their entry's color and would otherwise split into separate blocks.
- Selection and copy: `space` toggles the block under the cursor, `ctrl+o` copies the selected blocks (or everything visible when none are selected) and closes; `esc` peels one layer (text filter, then selection, then back to the list); `ctrl+x` quits Echo via `cmd.ErrQuit`/`handleQuit`; `q` closes. Browsing then leaving is a normal close, not `ErrCancelled`.
- `logview` is a META command: it must not reset `lastOutput`, so `copy-last` still copies the previous command; it is on the cmd-log skip list. The browser is TTY-guarded.
- Headless forms: `--list` (plain table), `--last` (opens the newest run), `--clear [--force]` (non-TTY without `--force` fails closed; local only), `--json`.
- **`--json`** prints the run list as a JSON array of `CmdLogMeta` to stdout only (no body lines; `Path` is not serialized). Empty history prints `[]` with exit 0, so "no runs yet" is data, not an error. It composes with `--from`/`--remote` and is rejected with `--clear` (exit 2). Source: Unit 96.
- **Remote history** (`--from`/`--remote`, `cmd.FetchRemoteCmdLogs`): one read-only SSH round trip streams every record under `${XDG_CONFIG_HOME:-$HOME/.config}/echo/cmd-logs/<ProjectKey(remote_path)>/`, split on a marker line (`@@ECHOLOGFILE <name>@@`; pretty-printed JSON and sanitized filenames cannot forge it). **Trap:** these are the records written by the Echo installed ON THE SERVER for that path, not the commands this laptop ran against it (those are in the local history with a `from` tag). The remote meta does not carry `deployed_tip` nor the unit 09 remote fields (`parseRemoteCmdLogs` does not copy them). Retention days are not shown for a remote (the server's own concern).

### `watch-deploy` record (Unit 96)

- Question it answers: did my commit auto-deploy? `watch` runs on the user's machine and command logs are LOCAL, so an agent reads `echo_cli logview --json` with no SSH. After each cycle that reaches deploy, `saveWatchDeployRecord` (`internal/cmd/watch.go`) writes one record under the LOCAL project history: `command: watch-deploy`, `cmd: deploy --commits <shas>`, `from` = target name or `remote`, `exit` 0/1, `deployed_tip` = the cycle's full tip SHA, and one INFO line (`watch-deploy ok|failed - modules=... commits=N tip=<short>`). Cycles that deploy nothing (rewritten branch, no commits, no deployable modules) write nothing; `[cmd_logs] disabled` suppresses it; the deploy's own output is not captured.
- Robust check: `git merge-base --is-ancestor <sha> <deployed_tip>`, because `watch` batches commits and the tip is the deployed frontier, not an exact SHA. How `watch` runs deploy (`deploy --commits <shas> --force --push`, `Via "watch"`) is owned by [deploy](deploy.md).
