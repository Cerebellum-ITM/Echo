# Modules and Odoo
> Owns how Echo runs module operations against Odoo: install/update/uninstall/test, `--level`, `update --last`, addons modes and discovery, i18n (including the Odoo 19 path as Echo implements it), modinfo/modstate/compare/view, migration detection and the XML lint. Last verified: 2026-09-30.

Deploy composes these primitives into releases: [deploy](deploy.md). Remote transport, targets and the remote prod gate: [remote-targets](remote-targets.md). `--json` and table output contracts: [ui](ui.md).

## How Odoo is invoked

- Module commands run a second, one-shot Odoo process inside the **already running** Odoo container: `<compose> exec -T <odoo> odoo <flags> --stop-after-init` (`internal/odoo/cmd.go`, `runOdoo`). Remote runs wrap the same argv in `ssh ... cd <path> && <compose> exec -T ...` ([remote-targets](remote-targets.md#ssh-transport)).
- **`compose exec` skips the image entrypoint** that turns `HOST/USER/PASSWORD` env into flags, so Echo passes the connection explicitly: `-d --db_host --db_port --db_user --db_password` (`odoo.Conn.Flags`, built by `buildConn` from `.env` `POSTGRES_*` and `cfg.DBContainer`). Empty values are skipped: an unset `POSTGRES_PORT` once produced a literal `--db_port=` that crashed Odoo with `ValueError: int('')`.
- **Odoo version is configured, not detected.** Local: `cfg.OdooVersion` (set by `init`; **defaults to `18` when unset**, so an unconfigured Odoo 19 project silently takes the legacy i18n path). Remote: the server profile's `odoo_version` (no default; empty shows `odoo=unknown`). `odoo.Major` returns 0 for empty/garbage and callers treat 0 as "legacy". No runtime `odoo --version` probe exists (Unit 53).
- The flag set for install/update/uninstall/test is the same on Odoo 17/18/19 and Echo does not branch on version for them. Only i18n (and `neutralize`, see [database](database.md)) differs.
- Local `install`, `update`, `uninstall` and `test` are never prod-gated; `i18n-update` is (red confirm on `stage=prod`, `--force` skips). The remote variants of `update` and `test` gate on the remote stage ([remote-targets](remote-targets.md#remote-prod-gate)).

## install / update / uninstall / test

- **install**: `-i <mods> --stop-after-init`, `--without-demo=all` unless `--with-demo`. No modules given opens the module picker (fail-closed without a TTY).
- **update**: `-u <mods>`; `--all` is `-u all`. `deploy` does not call this: it uses `odoo.InstallUpdate`, one run carrying both `-i` and `-u`, demo always skipped ([deploy](deploy.md)).
- **uninstall**: Odoo's CLI has no uninstall flag (`odoo --uninstall` exits 2 before touching the DB). Echo pipes a script into `odoo shell` that calls `button_immediate_uninstall()` (the Apps-menu path, which commits and reloads the registry). A module that is not installed makes the script `SystemExit` before removing anything, so the run is all-or-nothing (`odoo.UninstallScript`, b3086b0).
- **test**: `--test-tags /<mod1>,/<mod2>` (`--tags` replaces it verbatim; `--test-tags` already implies test-enable, never emit both), always `--log-level=test`, `--stop-after-init`. It does **not** pass `-u` by default: `--stop-after-init` starts a fresh process that imports edited Python from disk, so the fast loop skips the reload; `--update` opts into `-u` for XML/schema changes. Always `--no-http --http-port=8189` because the process shares the container with the live Odoo on 8069, and `--no-http` alone was observed ignored on Odoo 19 Enterprise (`odoo.Test`, `TestHTTPPort`). `deploy --test` uses the same isolation (`odoo.WithTests`).
- Remote `test` and `update` take `--from <target>`/`--remote` and need no local compose project; the connection comes from the remote profile. `update --last` is local-only and rejected remotely; unknown flags are an error for remote `update` but ignored by `test` ([remote-targets](remote-targets.md#remote-resolution-chain-and-flags)).
- A linked Reverb environment with a reachable API delegates `update` to Reverb's job instead of this path ([remote-targets](remote-targets.md#how-a-reverb-target-is-recognized-link-mode)).

### `--level`

- `--level <lvl>` / `--level=<lvl>` on install/update/uninstall maps to Odoo `--log-level=`. Valid set (identical on 17/18/19): `debug_rpc_answer debug_rpc debug debug_sql info warn error critical test notset` (`odoo.LogLevels`, validated before Odoo runs, `ErrInvalidLogLevel`). `extractLevel` runs first so the value is never read as a module name; a bare `--level` with no value is an error. `test` hard-codes `test`.

### `update --last` and the empty-picker repeat

- Persisted per (project key, db) at `~/.config/echo/last-updates/<ProjectKey>.toml` (`config/last_update.go`: modules, `all`, `level`, `saved_at`; the caller sets `SavedAt`, the config package stays clock-free). Written whenever an update **executes** (explicit args, picker, `--all`, `--last`) regardless of the exit status (re-running after a failure is the use case) and never on cancel.
- `--level` is stored and inherited unless overridden. **`--i18n` is not stored**, so `update --last` can never silently overwrite translations.
- `--last` excludes module names and `--all` (`ErrLastExclusive`); no record is `ErrNoLastUpdate`. Previous-run modules are tinted `palette.Info` in the picker.
- Enter on an empty picker offers "repeat last update", but only when `ModulesOpts.Interactive` is true (the interactive REPL). One-shot `update` and recipes never prompt: an empty selection cancels, while the record is still saved. The picker distinguishes Esc (`canceled`) from an empty confirm (`runFuzzyPickerCore`); `runFuzzyPicker` keeps cancel-on-empty for install/uninstall/test.

### `update --installed` and `--i18n`

- `--installed` only swaps the picker's candidate source to the installed rows of `ir_module_module` (the same query as `modstate`) so core modules like `base` are pickable; the project picker never lists them. It is inert (no error) with explicit modules, `--all` or `--last`.
- `update --i18n` appends `--i18n-overwrite` to the same `-u` run and overwrites **all active languages**. Odoo's `-l/--language` only scopes `--i18n-export/--i18n-import`, never `-u`; a per-language overwrite is `i18n-update <mod> <lang>`. Plain `-u` reloads terms from `.po` but keeps saved DB translations. `--i18n` is a boolean for that reason (Unit 49). How deploy decides to add it: [deploy](deploy.md).

## Addons: modes and discovery

Where a project's modules live is resolved in two places that must agree: the host (for push, deploy, lint, i18n, pickers) and the container's `odoo.conf` (when addons live only in the image).

- **Two addons modes** per project (`AddonsMode`): `host` (default; `addons_paths` are host folders relative to the root) and `conf` (absolute **container** paths read from `addons_path` of the instance's `odoo.conf`, `conf_path` default `/etc/odoo/odoo.conf`; modules listed inside the container with one `sh -c` pass over `*/__manifest__.py`).
- `resolveModules` (`modules.go`): in `conf` mode the conf is re-read live on every listing and the saved paths refreshed if they changed. In `host` mode it lists host addons; only if that finds **nothing** (including the discovery walk below) does it try the container conf, and if modules are found it flips the project to `conf` and **persists** `addons_mode` + paths. That fallback is the origin of conf mode (Unit 26: addons only inside the container on a prod-like instance).
- `modules --config` (huh folder form) always pins `host` mode, the escape hatch. `modules --addons-path a,b,c` writes the key without the form (headless agents cannot drive it), pins `host`, rejects absolute or `..`-escaping paths, and an empty list clears the key.
- **Enterprise dirs are dropped from the picker list**: `parseAddonsPath` ignores entries whose basename starts with `enterprise` (case-insensitive). **Trap:** that filtered list must never build the Odoo 19 ephemeral conf, because `-c` replaces the real conf and a module may depend on Enterprise; i18n reads the raw value with `extractAddonsPath` ([i18n](#i18n)). A mode that updates Enterprise modules was noted as a possible future option, not built.

### Discovery (Unit 115, `addons.go`)

- Before this unit **four independent one-level lookups disagreed** (`resolveModuleDir` config-aware for push/i18n; `isAddonDir` config-blind in deploy, so `deploy --modules` failed where `push` worked; lint's `hostAddonsRoots`; the picker's lister), plus a fifth: git-path to module mapping by first path segment, so `--dirty`/`--auto` saw nothing in nested layouts. One resolver is the anti-drift measure; add new module lookups through it, not a new loop.
- Order (`resolveAddon`, `listAddons`): configured `AddonsPaths` (not when `AddonsMode == conf`, whose paths are container paths and cannot be walked on the host) > default roots `.`, `addons`, `custom` > bounded walk (`discoveryMaxDepth` 3, skips hidden dirs and `skipDirs`, never descends into an addon). The walk is a fallback, so configured projects pay nothing. **Nothing discovered is persisted**: writing `AddonsPaths` as a side effect of `push` would pin a snapshot of the tree.
- Same module name under two roots is `ErrUsage` naming both: a silent pick is the bug class being removed.
- **Silent-failure trap:** an argument with a separator (`push sub/<mod>`, shell tab-completion) used to flow the slash into the remote destination, syncing to `addons/sub/<mod>`, which an earlier `addons_path` entry (`/mnt/extra-addons`) shadows: the push reports success, `-u` is clean and the change never loads. Now an argument with a separator resolves to its basename or is `ErrUsage`, so the module name that reaches logs and remote paths never contains a separator (`resolveAddonPath`).
- `addonFromPath` maps a repo-relative path to its owning addon (ancestors probed shallowest first, depth-capped at 3).
- **Not yet routed through the resolver (verified in code):** `view`, `modinfo` and the container side of `compare` still loop over `AddonsPaths` or the default `.`, `addons`, `custom` one level deep (`moduleBase`, `moduleManifest`, `containerAddonsPathsFor`). The local checkout side of `compare` does use `resolveModuleDir`. A module that only discovery finds works for `push`/`deploy`/`i18n`/`lint` but not for `view`/`modinfo`.
- Project root for projectless one-shots: when no `docker-compose.yml` is found, `main.go` `repoRoot` uses the git top level (else the cwd), so a subdirectory of a link-only repo keeps the root's per-project state (`project.FindRoot` itself only walks up for a compose file). Migration of state written under a subdirectory: [architecture-and-traps](architecture-and-traps.md).

## i18n

Commands: `i18n-export <mod> [lang]` (local container to host), `i18n-update <mod> [lang]` (host `.po` to local DB), `i18n-pull` (remote DB to local `.po`). Default language `es_MX`; one module per export/update call.

- **Host/container exchange** uses a container-side temp file `/tmp/echo-i18n-<nano>-<rand>.po` plus `docker cp`, never a bind-mounted addons path, so it works whatever the compose mounts. Cleanup is best-effort and always runs. `--out` is export-only. Export writes to `<addons>/<mod>/i18n/<lang>.po` of the module's resolved dir (created if missing). `i18n-update` imports with overwrite and requires an existing `.po` (`ErrTranslationMissing`).
- **Odoo 19 (`odoo.Major(version) >= 19`)** dropped `--modules/--i18n-export/--i18n-import`. Echo uses `odoo i18n export|import`, whose only connection inputs are `-c <conf>` and `-d`:
  - `odoo i18n export -c <conf> -d <db> -l <lang> -o <file> <module>`; `odoo i18n import -c <conf> -d <db> -l <lang> -w <file>` (`-w` replaces `--i18n-overwrite`; import takes no module argument; one language only). Do not add `--no-http` or `--stop-after-init`: the subcommand injects/exits itself (`ExportI18n`, `UpdateI18n`).
  - Credentials ride in an **ephemeral `odoo.conf` written inside the container** per invocation (`odoo.RenderConf`, `writeContainerConf`) and removed with the temp `.po`. Bonus: the DB password stays out of the container's `ps`.
  - **The conf must be written through stdin** (`sh -c 'cat > path'` via `docker.ExecWithStdin`; remote: `runSSH` with stdin). A plain `docker cp` lands it `root:root 0600`, unreadable and unremovable by the non-root `odoo` user in sticky `/tmp`.
  - **The conf must carry the real `addons_path`**, read raw (unfiltered, Enterprise kept) from the container's own `odoo.conf` (`containerAddonsPath`, `remoteAddonsPath`; the profile's stored `AddonsPaths` is only a fallback because it is a stale, filtered snapshot and host-relative in host mode). `-c` replaces the real conf: without it project modules are "not installable, skipped" and the `.po` is incomplete with ERROR lines marking the run failed.
  - Rejected: libpq `-e PGHOST...` env on `compose exec` (spreads connection state per call site; Echo passes connection deliberately).
- **`i18n-pull`** (Units 50, 76, 77, 99) runs from a pure addons repo (projectless one-shot):
  - Candidates come from the **remote project's own addons** (profile `addons_paths`, else the remote `odoo.conf`), not from `ir_module_module`: the DB list returned every stock Odoo module. `--installed` keeps the DB list as the escape hatch. Source/target resolution: [remote-targets](remote-targets.md#remote-resolution-chain-and-flags).
  - Per module: export to a temp `.po` in the remote container, `cat` it back over SSH, best-effort `rm` (on 19, plus the conf write). An **empty `.po` is skipped**, never overwriting the local file. Read-only against the remote DB.
  - Module-vs-language: `--lang` explicit means all positionals are modules; with 2+ positionals a trailing locale-shaped token (`^[a-z]{2,3}(_[A-Z]{2})?(@[a-z]+)?$`) is the language; a single positional is always a module (`parseI18nPullArgs`).
  - Batch (`--all` or more than one module): a failing module is skipped with a WARNING and the run ends `pull complete pulled=N skipped=M`; a single module fails fast. The build-mode composer bakes `--lang=<lang>` (not a trailing positional) so the line round-trips through the parser; a test pins the pair ([scripting](scripting.md)).
  - Destination: the module's real host addons dir if it exists locally (resolver-aware), else cwd-relative `<root>/<mod>/i18n/<lang>.po`. `--to-worktree[=<branch>]` only redirects the local root where the file lands (bare form opens a picker over other worktrees and does not consume the next token); it is resolved before any SSH and is not offered by build mode.
  - It does not go through the Reverb context (reads the server profile directly); `-E` is refused for it until Unit 122 deletes `-E`.
- Open follow-ups: stream i18n logs live; a flag that prints the generated `odoo.conf`. Odoo 19 export/import against a real instance has no recorded verification beyond the bug fixes above ([operations](operations.md)).

## modinfo and modstate

- `modinfo [mod]` (read-only): one `psql -At` over `ir_module_module` (`name|latest_version|state`) plus one manifest read; one `echo.modinfo` Odoo-style line, never a table. The manifest source follows addons mode (host `ReadFile` vs `docker exec cat` in conf mode).
- **The DB stores the adapted version.** Odoo's `adapt_version` prepends the series (`17.0.`) unless the version already starts with it, so the manifest version must be normalized with `cfg.OdooVersion` before comparing, else `1.3.0` vs `17.0.1.3.0` reports a false `update pending`. Odoo's literal quirk is kept (`adaptVersion("17.0","17.0") = "17.0.17.0"`); an empty series compares raw (`adaptVersion`, `odooSerie`).
- Verdicts (`computeStatus`): `not installed` (no row or state other than `installed`), `no version`, `in sync`, `update pending` (manifest > DB), `db ahead` (DB > manifest). Segment-wise numeric compare, missing segments count as 0, string fallback for non-numeric. INFO for `in sync`, WARNING otherwise; one-shot eligible so CI/recipes can assert "in sync".
- **Limit:** the manifest version is extracted by regex (`['"]version['"]\s*:\s*['"]...['"]`), not a Python parser; a version computed dynamically in `__manifest__.py` is invisible. `modinfo --last` is session-only memory, deliberately not persisted (unlike `update --last`).
- `modstate [--all] [--json]` lists module states, installed-only by default in **both** modes (`--all` is the only widening flag, so the JSON contract does not depend on an output flag). `--json` writes only the marshaled array to stdout (no ANSI, no log line, errors to stderr, exit 0/1/2 uniform); NULL `latest_version` is JSON `null`, and in the `-At` query the NULL flag is the last column so the `|` split is unambiguous. It never runs `odoo` and needs no TTY.

## view and compare

- `view <mod>` browses a module's files and prints one; display chain is `bat`/`batcat` then Echo's internal themed print, with **no `cat` tier** (it does not highlight and bypasses Echo's output capture). The internal print is captured for `copy-last`; `bat` output is not. `view --last` is session-only and re-reads the file fresh. Remote `view --from/--remote` is read-only (no prod gate) using the host-then-container probe ([remote-targets](remote-targets.md#host-filesystem-vs-container-probe)).
- `compare <mod>` diffs a local checkout file against the deployed copy: container/remote copy is OLD (`---`), local checkout is NEW (`+++`), so `+` reads "my changes not in the container". Computed in-process with `go-difflib` (no external `diff` on either side). The local side is always the host checkout (a module with no host copy is an error, never container-vs-container). A file missing in the container diffs against empty with a WARNING. Exit 0 for identical and different (a viewer, not a CI check). With a bind-mounted local project both sides are the same file, so an empty diff doubles as a "mount is live" check.
- `compare --all`: one hashing command per side instead of N reads. Local MD5 in-process; container via one `find <dir> -type f -exec md5sum {} +` (one `exec` or one SSH round trip; BusyBox and coreutils output both parse). Statuses `changed/added/missing/equal`, only non-equal rows listed; a module absent in the container is all `added`. A missing `md5sum` is not worked around. The drill-down (pager and pickers interleaved) lives in the REPL layer, TTY only; non-TTY prints the table and exits 0.
- `compare --targets <a>,<b> [<mod>...]` compares two connect targets' [deploy locks](deploy-safety.md#deploy-lock), not files (`RunCompareTargets`, `internal/cmd/compare_targets.go:138`; Unit 130). Exactly two names, each a pure lookup in `cfg.ConnectTargets` (`resolvePullRemote`): no picker, no link binding, no `env:`. `ErrUsage` (exit 2) before any SSH for one or three names, a repeated name, an unknown name, two targets with the same `ssh_host` and `remote_path`, and `--targets` with `--all`, `--from`, `--remote` or `-E`/`--env` (`validateTargets`, `internal/cmd/compare.go:108`); `--json` without `--targets` is also `ErrUsage`. It reads one `cat` of `.echo/lock.json` per target, `a` then `b`, and no server profile; it writes nothing and is never stage-gated.
  - **Statuses** (`targetStatus`, `compare_targets.go:254`), per module in the union of both locks or in the positionals: `only <target>` when one side has no entry (Echo never recorded shipping it there; not "absent from the server"), `unknown` when either entry is `dirty` (`reason=dirty`), no identity can be derived (`no-identity`; also a named module neither lock has) or a lock could not be read (`unreadable`), `same` when both identities are equal trees or both entries are clean with the same sha, `differs` when both are trees and differ.
  - **Identity is the module's git tree, not the sha** (`lockIdentity`, `:315`): the entry's `tree`, else `git rev-parse <sha>:<module path>` in the local repository; none when the entry is dirty, the sha is not local or the module is not in the local checkout. So the same content shipped as `worktree@X` and `ref@Y` is `same`.
  - **Lock base**: on a git-deploy side, a module without an entry is read as `base@<sha7>` from the lock base (`sideCell`, `:237`); absent at the base sha it is `only` the other side, a base sha not in the local repository makes it `unknown`. In `--json` that cell is a synthesized entry with `source: "base"`.
  - **Output**: one `echo.compare.targets` line per side (`lock target= modules= unverified= …` from `lockSummaryFields` plus `base=branch@sha7`; `no deploy lock`; or an ERROR for `unreadable`/`corrupt` with the reason), a `Line{Kind:"table"}` table of the rows that are not `same` (positionals always print; `differs` warn, `only` info, `unknown` faint; cells are `label()` plus version plus `unv.` while unverified), and `targets compared a= b= same= differs= unknown= only_<a>= only_<b>=`. All `same`: the closing line only. `newer=` (JSON) names the side whose manifest version `compareVersions` orders higher. One side failing still shows the other (every row `unknown`); both failing print both ERRORs and no table.
  - **Exit**: 0 when both locks were read (found or absent), whatever the differences; 1 when either is `unreadable` or `corrupt` (the output, JSON included, is still emitted); no auto-copy. `--copy` puts the plain table and closing line on the clipboard; `--json` writes one object (`a`, `b` with `name`, `host`, `path`, `lock`, `error`, `base`; `modules` with every row whatever its status; `counts` with `only_a`/`only_b`) to stdout and the lines to stderr. The local working tree is never a side ([decisions](../decisions.md#deploy-safety)). Build mode does not offer `--targets` or `--json` (`buildOmittedFlags`, `internal/repl/build.go:36`).

## Migration detection

- Passive observer on the existing output stream (`repl/migration.go`), no extra Odoo call: matches `odoo.modules.migration: module X: Running migration [VER>] (pre|post|end)-migration`, collapses per module+version and trims the trailing `>` range marker. Summary lines `echo.<cmd>.migration` print **after** the success/failure recap, also on failure. `report` re-scans every step of the last run ignoring `--step`/`--level`, because migrations are INFO and `--min-level=warn` would hide them ([scripting](scripting.md)).

## Lint (`lint`, Units 109-111)

`lint` checks Odoo XML the way the server's data loader does, offline: no container, DB or network, so it is safe on every save. It is a projectless one-shot (a git hook or editor runs it where the file was saved). Exit 0 when no blocking finding, non-zero when any `err`; `--json` for machines.

- **Why it exists:** a `--` inside an XML comment (`Double hyphen within comment`) and `t-translation="off"` on a `<template>` (`Element odoo has extra content: template`) each cost a failed deploy; the only defence was a handoff note the agent then tripped on twice. A check that has to be remembered is not a check, hence exit codes for hooks/CI.
- **The loader validates every manifest-listed data file against `import_xml.rng`** (`odoo/tools/convert.py`). That grammar is byte-identical in Odoo 17, 18 and 19 (11,407 bytes), so one embedded copy serves all; `grammarByMajor` is the extension point and a test pins the hash. It is **embedded** rather than read from a local Odoo tree or fetched from the instance: a missing source tree would silently degrade on every machine that never downloaded Odoo, and a fetch would make an offline check depend on the network. An unknown major falls back to the newest grammar with a WARNING.
- **`xmllint` is the authority; Go `encoding/xml` is the unskippable floor.** Go accepts duplicate attributes, two roots and a mid-document `<?xml?>` that the server (libxml2 via lxml) rejects, so Go-only would say "lint clean, deploy aborted". Rejected: cgo libxml2 (breaks the cross-compiled release binaries) and a pure-Go RelaxNG. Findings dedupe by `(file,line,rule)` with the libxml2 message winning. When `xmllint` is missing the schema and libxml2 passes are skipped with a WARNING naming what was skipped (`SkippedPasses`); a validator that is missing never fails the run and never claims a clean result for checks it did not run.
- **Severity is one axis, manifest-aware** (`applySeverity`): a finding in a file listed in `data`/`demo` is `err`; in an unlisted file it is `warn`. Without it the lint would be stricter than the server, which a pre-flight must never be.
- Rules (stable keys for hooks/CI): `xml-syntax`, `xml-syntax-embedded`, `odoo-schema`, `manifest-missing`, `manifest-unlisted`.
  - `manifest-missing` (listed in `data`/`demo` but absent on disk) is always `err`: the loader aborts every time, and it is anchored to the `__manifest__.py` line; it covers non-XML entries (a missing `ir.model.access.csv` aborts too).
  - `manifest-unlisted` is always `warn`, never `err`: blocking on an unlisted `.xml` would make the pre-flight unusable. It qualifies only data-shaped files (`<odoo>`/`<openerp>` root, not OWL `<templates>` delivered via assets) and skips `static/ tests/ migrations/ i18n/`. `selfSeverityRules` stops `applySeverity` from rewriting either.
- Only `arch`/`arch_db` values are re-parsed as XML sub-documents. `body_html` is HTML parsed by `lxml.html` (tolerates unclosed `<p>` and `%` directives); checking it as XML produced false positives, and the fix was to not check it, not to soften the severity. Findings inside a sub-document report the line of the **containing** file.
- **A clean lint means "does not break on markup", not "loads".** xpath anchors, missing xml_ids and model/field names need a real registry; view-arch grammars (Odoo has no `form_view.rng`) are out of scope.
- Measured (Unit 109): 356 files in 0.27 s on a large real repo, one module 0.03 s.
- Scope for modules: `hostAddonsRoots` (configured roots plus discovery). `LintModules` reports modules it cannot find locally instead of failing: a deploy selection may name a module that only exists on the server.
- The deploy pre-flight (placement before the first SSH, `--no-lint`, blocking only on `err`, linting the tree that ships) is owned by [deploy](deploy.md).
